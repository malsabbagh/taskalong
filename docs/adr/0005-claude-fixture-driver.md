# Versioned Claude fixture driver

Status: proposed for review in M5.

Keep one Workflow, Store, durable supervisor and owned bounded runner. A second
vendor lifecycle would duplicate authority, cancellation, reservations, effect
reconciliation and acceptance. Instead the closed registry selects an exact
(task version, registered projection, configuration kind, configuration version)
contract with a packet compiler, semantic representability check and driver.
Unknown tuples refuse; discovery of a binary never registers a driver.

The separate immutable `DriverConfig` 2.3 describes the Claude fixture launch.
`ProviderProfile` 2.0 independently describes the requested model and simulated
route. The existing v1 RuntimeProfile remains a v1 runtime profile: neither its
adapter enum nor its digest fields acquire a new meaning. TaskSpec 2.3 names a
binding and `driver_config_digest`. Its packet/result/projection use explicit
configuration, provider and fresh attempt-session references. The canonical
packet is also the exact stdin wire packet; the mapping binds the immutable
admission and both packet identities. No opaque Codex session is transferable.
The existing separately bound v1 independent check profile still issues verifier
evidence. Worker completion and a successful structured result cannot accept a
candidate without current independent checks and the pinned review contract.

Executable 2.3 state requires explicit backed-up quiescent migration from format
3 to 4. SQL004 adds a compatibility fence, not another history store. Existing
immutable tables retain typed configuration documents. Both version markers and
the migration receipt commit together. A pinned format-3 client refuses the new
format before writes. Previous backups are private; restoration uses a verified
fresh destination and retains prior state. Migration is never implicit at submit
or start, and schema reading alone does not require a store.

The only new registered projection is `claude-print-fixture/1`, with installation
version `synthetic-claude-1`. It uses an original external synthetic program,
never the installed vendor executable. Only empty additional instructions,
semantic tool `claude.edit` (wire tool `Edit`), the synthetic sandbox backend,
closed print/stream/schema argv, exact requested model and a fresh attempt UUID
are representable. Task contents go through stdin. The child receives a private
HOME/config/temp and a minimal environment without credential values. Unknown
policies/routes, auxiliary models, non-null hard token/cost caps and production
requests refuse. No arbitrary argv, shell strings, fallback model, approval
bypass or background/session continuation is admitted.

Current mutable trust, authority, executable fingerprints, deadlines and budget
remain checked before preparation/dispatch and at the owned gate. Configuration
and trust revocation are declaration operations: an absent/changed executable
must not prevent recording revoked trust. The exact executable is checked when
execution is attempted. Malformed/denied/mismatched streams, nonzero exits,
output/time limits and unaccounted descendants cannot become worker success.
Unknown effects stay quarantined. Restart uses a new attempt/session and consumes
the same persisted budget; native resume is explicitly unsupported. Reported
usage is retained with unknown scope and never becomes known token/cost totals.

Installed Claude 2.1.220 help/version were inspected without inference. They do
not qualify these synthetic frames or prove actual managed instructions, tools,
auth/routing, complete lifetime or cancellation. Current vendor documentation
can describe later versions. Safe/bare/settings flags are not containment proof,
and bare changes credential discovery. Production remains disabled until a
separate exact-version, exact-mode qualification; Ollama routing is a later
milestone. No registry publication follows this change.

The private Linux helper/status reader use protocol 2 as a matched package pair.
A separate `not_released` terminal describes EOF at the closed gate before any
fork, with null target identities/exit and a kernel no-child check. It confirms
cleanup only when the owner never attempted release, reaped the wrapper with
protocol exit 0, proved its group ceased and read the complete status-channel EOF.
Version/type/field/sequence errors and partial/post-terminal data remain unknown.
Started targets retain positive root PID/PGID and signed exit semantics; a
missing root identity is never generic cessation proof. Invalid gate tokens,
read/fork errors, killed/stopped wrappers and ambiguous descendants cannot use
the no-target path. Both drivers retain `cancel_pending`, `not_sent` and actual
confirmed ProcessResult requirements. No cancellation authority, task success,
production support or runtime qualification follows from parsed status alone.
