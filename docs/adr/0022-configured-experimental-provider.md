# Configured experimental local provider execution

Status: proposed; local configuration enables the experimental route.

The user's product requirement replaces the development-only permanent refusal:
a locally configured Muse provider must be usable through normal TaskAlong
configure-provider/run/status/result operations. There is no additional production
activation, opaque proof receipt or unconditional live gate in this route.
Existing production-qualified workflow contracts remain separate.

Selected seam: RunService delegates the named provider to an original local adapter.
Alternatives of manually invoking an external CLI or reusing production-qualification
admission would respectively bypass the product or impose unrelated guarantees.
Configuration is the trusted OS-operator control plane; task/response JSON cannot
configure a provider, inject argv or grant permissions. The adapter fixes its tool
and manual-review posture, preserves native account ownership and never takes a key.

Context defaults to include preconfigured provider context. Full exclude is an
explicit option that fails with the current native client's real limitation;
native-only is explicitly partial. Optional context fingerprints bind a reviewed
snapshot without becoming a mandatory activation flow. A local fixed Echo check
screens startup context and records its scope; it never masquerades as live model
execution. provider-context exposes the same check as an optional private local inspection,
without a submission claim or any Meta invocation. Stable message fingerprints
can bind user rules as well as catalog and vendor templates. No actual
account/context/login data or paths enter source fixtures.

One immutable Store and bundle claim precedes real process release. The existing
bounded foreground owner captures one Meta invocation and local observations;
there is no controller retry, fallback, automatic apply or acceptance. Unknown
native retries, remote accounting and descendant cessation are retained honestly,
not treated as production-qualification requirements. A bad response/failure
retains original capture and prevents redispatch. Event files append, while the
Store setting is only the latest read-only status/result index.

Validation covers normal configured dispatch, default context inclusion, honest
exclusion failure, data screening, one-use claims, normal CLI/API/result behavior,
output binding and manual proposal staging using explicit synthetic fixtures.
A bounded real test must be reported separately and only after actual observation.
No new Store/schema migration is needed; rollback leaves claims/history intact.

Capture admission additionally measures the generated prompt against the supported
session protocol's two complete input echoes, using minimal JSON framing and
UTF-8 escaping. A known-insufficient whole-protocol cap refuses before any native
process or submission claim. A local provider-budget query exposes this lower
bound; it does not promise response fit or replace runtime cancellation. The
adapter separately caps canonical decoded proposal bytes and records retained
buffer counts separately from all drained bytes. It never omits protocol records
to manufacture success. Existing caps/defaults remain finite; old configuration
identities remain readable without rewriting receipts or claims.
New configurations use format `/2` to prevent older clients from silently
ignoring the added proposal bound; legacy `/1` remains readable by this client.
